# Text-to-SQL Analytics Agent

AI Engineering · Generative AI · Agentic AI · Database Analytics

An intelligent analytics assistant that converts natural-language questions into
**safe** SQL, runs them against a relational warehouse with a read-only account, and
returns tables, charts and an AI-written business summary.

## How a question flows

```
user question
   │
   ▼
Schema Agent        picks only the tables the question touches + literal values
   │
   ▼
SQL Generator       LLM (Ollama/Qwen2.5-Coder) → one SELECT statement
   │
   ▼
SQL Validator       SQLGlot: read-only, allow-listed tables/columns, row cap
   │
   ▼
Query Executor      runs on the read-only connection, timeout + row limit
   │
   ▼
Result Analyzer     AI summary and insights
   │
   ▼
Visualization Agent KPI / line / pie / bar / table as plotly JSON
```

Both validation failures and execution errors enter a bounded repair loop (max 3
attempts) so the model gets a chance to correct its own SQL before the question is
rejected. Nothing generated by the LLM reaches the database without passing the
validator first.

## Quick start

### 1. Database

With Docker (full PostgreSQL path):

```bash
docker compose up -d db
```

`database/schema.sql` and `database/sample_data.sql` are applied automatically on the
first start (400 orders, ~1000 line items across 2025–2026).

Or run the bundled SQLite demo — no database server needed:

```bash
cd backend
python scripts/init_demo_db.py            # creates data/analytics.db
```

### 2. Backend

```bash
cd backend
python -m venv .venv && .venv\Scripts\activate      # Windows
pip install -r requirements.txt
copy .env.example .env                              # then edit
uvicorn app.main:app --reload --port 8000
```

Open the interactive API docs at <http://localhost:8000/docs>.

### 3. Local LLM (optional but recommended)

```bash
ollama serve
ollama pull qwen2.5-coder:7b
```

Pick the model to match the machine: `qwen2.5-coder:3b` (≈1.9 GB) answers well on
8 GB of RAM with no dedicated GPU, where `7b` would spend most of its time swapping.
Ollama can also be run from its portable zip — `ollama.exe serve` needs no installer
and no admin rights. If `/api/generate` answers 404, the endpoint is fine and the
model is simply not in the library yet; `/api/v1/health` says so explicitly.

If Ollama is not running, the agent automatically switches to a deterministic
rule-based generator so the pipeline stays fully usable offline — the response
tells you which provider answered.

### 4. Frontend

```bash
cd frontend
npm install
npm run dev
```

<http://localhost:5173> — the Vite dev server proxies `/api` to `:8000`.

## Configuration

All backend settings live in `backend/.env` (see `.env.example`).

| Variable                | Meaning                                                    |
| ----------------------- | ---------------------------------------------------------- |
| `DATABASE_URL`          | Introspection URL (PostgreSQL or `sqlite:///./data/…`)     |
| `READER_DATABASE_URL`   | Read-only URL used to execute generated SQL                |
| `LLM_PROVIDER`          | `ollama` or `heuristic`                                    |
| `OLLAMA_MODEL`          | e.g. `qwen2.5-coder:7b`                                    |
| `ALLOWED_TABLES`        | Table allow-list enforced by the validator                 |
| `HIDDEN_COLUMNS`        | Columns the agent may never read (e.g. `customers.email`)  |
| `MAX_ROWS`              | Row cap injected into every query                          |
| `QUERY_TIMEOUT_SECONDS` | PostgreSQL `statement_timeout`                             |

Which database is live is not an `.env` setting: activating a source clones these
settings with its own URL, table list and name, and publishes the copy through
`get_settings()` so the whole pipeline — schema retrieval, validator, executor,
explorer — follows the new database without a restart.

## Bring your own data

The **Sources** page (`/sources`) accepts four kinds of datasource. Register one, press
**Use**, and every later question runs against it until you switch back.

| Source                       | What happens                                                                 |
| ---------------------------- | ---------------------------------------------------------------------------- |
| One `.db` / `.sqlite` file   | Copied into `backend/data/uploads/<id>/` and opened **read-only** by the driver |
| CSV / TSV / Excel tables     | One table per file (or sheet) built into a local SQLite file; headers are renamed to SQL-safe identifiers and blank columns dropped |
| `.sql` dump                  | Only `CREATE TABLE` and `INSERT` statements are replayed — `DROP`, `UPDATE`, indexes and `COPY` are skipped and reported |
| `postgresql://` / `mysql://` | Probed for the table list, then used with your own credentials                |

Upload limits: 100 MB per batch, 40 files, 100 tables, and only one kind of source per
registration. Uploaded filenames are sanitised before staging, so `../../../evil.db`
lands inside its own folder.

**Without Ollama** an unknown schema is still answerable. The offline generator reads
the live catalog and picks a shape from the question — row counts, `SUM`/`AVG` over a
measure it infers from the column types, groupings by a category or label column,
month buckets over a date column, and `WHERE` filters built from values the question
actually names (distinct values are profiled at schema-load time, capped by table size
and column budget). Starter questions on the Ask page are generated from the same
catalog, so they only ever reference tables you have.

> **Heads-up:** a pasted connection string — password included — is stored in
> `backend/data/datasources.json` so the source survives a restart. That directory is
> git-ignored; use a `SELECT`-only role and delete the source when you are done.

## Safety model

Defence in depth — each layer holds even if another is bypassed:

1. **Parser gate** — SQLGlot parses the SQL; anything that is not exactly one
   `SELECT`/`WITH … SELECT` is rejected. `INSERT`, `UPDATE`, `DELETE`, `DROP`,
   `CREATE`, `ALTER`, `GRANT`, `COPY` and multi-statement strings never pass.
   `ATTACH`, `DETACH` and `PRAGMA` are blocked too, so a SQLite source cannot be
   pointed at another file or load an extension.
2. **Table allow-list** — queries referencing unlisted tables are blocked; CTE
   aliases are correctly excluded from the check. For an uploaded source the list is
   rebuilt from that source's own schema at activation, so it is never a guess.
3. **Column protection** — protected columns are blocked whether named directly or
   covered by `SELECT *`.
4. **Function block-list** — `pg_sleep`, `lo_import`, `dblink`, `load_extension`, file readers etc.
5. **Row cap** — `LIMIT` is injected when missing and reduced when too large.
6. **Database role** — `analytics_reader` has `SELECT` only, and the connection sets
   `default_transaction_read_only` plus a `statement_timeout`. SQLite sources are
   opened with `?mode=ro`, so an `INSERT` fails in the driver before it reaches SQL.
7. **Ingestion gate** — uploads are staged under a generated id with a sanitised
   filename, size- and count-capped, and a `.sql` dump is filtered by statement type
   before a single statement runs. Connection strings are never returned by the API.

## API

| Method   | Endpoint                  | Purpose                                                |
| -------- | ------------------------- | ------------------------------------------------------ |
| `POST`   | `/api/v1/ask`             | Question → SQL, results, summary, chart                |
| `GET`    | `/api/v1/schema`          | Allow-listed schema for the explorer                   |
| `POST`   | `/api/v1/sql/validate`    | Dry-run hand-written SQL through the validator         |
| `GET`    | `/api/v1/history`         | Recent runs (conversation memory)                      |
| `GET`    | `/api/v1/history/{id}`    | Full run including result set                          |
| `DELETE` | `/api/v1/history`         | Clear history                                          |
| `GET`    | `/api/v1/export/{id}`     | `fmt=csv\|xlsx` download                               |
| `GET`    | `/api/v1/suggestions`     | Starter questions, generated from the live schema      |
| `GET`    | `/api/v1/health`          | Database, LLM, active source and limit status          |
| `GET`    | `/api/v1/datasources`     | Registered sources (connection secrets are stripped)   |
| `POST`   | `/api/v1/datasources/upload` | `multipart/form-data` with one or more `files`      |
| `POST`   | `/api/v1/datasources/connection` | Register a PostgreSQL/MySQL DSN                |
| `PUT`    | `/api/v1/datasources/active`  | Activate a source by id · `null` returns to the demo   |
| `DELETE` | `/api/v1/datasources/{id}`    | Remove a source and delete its staged files           |

## Tests

```bash
cd backend && pytest ../tests -v
```

- `test_sql_validator.py` — the safety guarantees (DML/DDL blocked, allow-lists,
  hidden columns, row caps, CTEs, dangerous functions, `ATTACH`/`PRAGMA`).
- `test_query_executor.py` — read-only execution, row capping, error capture.
- `test_agent_pipeline.py` — end-to-end questions, rejection, follow-up memory and
  CSV/Excel export against a seeded demo database.
- `test_datasource.py` — upload guards (type, size, path traversal, mixed kinds), dump
  filtering, CSV header sanitising, DSN handling, activation and rollback to the demo.
- `test_generic_offline.py` — the offline generator over a schema it has never seen:
  counts, sums, averages, groupings, value filters and the starter questions.
